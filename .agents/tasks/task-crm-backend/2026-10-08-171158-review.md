# CRM Sales Management System — Full Backend Implementation

This is a complete Node.js/Express REST API for a CRM system, implementing authentication with JWT token rotation, CRUD for leads/customers/deals/activities, a transaction-backed lead conversion flow, and role-based access control across three user tiers. The change is the entire backend — no prior implementation exists. One blocking defect exists in `auth.service.js` that causes every auth endpoint to crash at runtime, and a secondary business-logic gap allows stage transitions to bypass their own validation rules.

**Watch for:**
- **confirmed** — `auth.service.js` destructures `{ User }` from a module that exports the model directly (`module.exports = User`). `User` is `undefined` at runtime. Every call to `register`, `login`, `logout`, and `refreshTokens` throws `TypeError: Cannot read properties of undefined (reading 'create')` before any user data is touched.
- **confirmed** — `PUT /api/deals/:id` accepts `stage` in its body (via `updateDealSchema`) and routes directly to `updateDeal`, which calls `findByIdAndUpdate` with no stage-transition validation. A `sales_executive` can move any deal to `won` or `lost` without providing `lostReason`, without `probability === 100`, and without the terminal-stage admin guard — bypassing all enforcement that exists in `updateDealStage`.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The project structure is clean: six Mongoose models, three middleware files, six Zod validators, eight services, eight controllers, eight route files, plus `app.js` and `server.js`. The layering is consistent — controllers are thin pass-throughs, all business logic lives in services, and errors propagate to the global handler via `next(err)`. The only structural deviation is in `auth.service.js`, where a wrong import pattern renders the entire authentication layer non-functional at runtime.

The deal pipeline enforces stage-specific rules through `updateDealStage` — won deals require value, probability 100, and a close date; lost deals require a reason; only admins can reopen terminal deals. That enforcement is entirely bypassed by the general `updateDeal` path, which accepts `stage` as a free-form field. The fix is to strip `stage` from `updateDealSchema`, making stage transitions exclusively accessible via `PATCH /deals/:id/stage`.

`convertLead` uses array-form `Model.create([doc], { session })` — the required pattern for including documents in a Mongoose transaction — creating Customer, Deal, and three Timeline entries atomically, with `session.abortTransaction()` in the catch block.

Security posture is solid for a development-phase API: `helmet`, `cors`, `express-rate-limit` are applied globally; refresh tokens are stored in `httpOnly` cookies with `sameSite: strict`; `password` and `refreshToken` are `select: false` on the User schema and stripped by `sanitizeUser` before any response. One gap: when `ALLOWED_ORIGINS` is unset, the CORS config falls back to `'*'`, which is permissive. The spec did not define this fallback, and it should default to restrictive rather than open.

## Auth service import crash

`auth.service.js` line 3:

```js
const { User } = require('../models/User.model');
```

`User.model.js` exports `module.exports = User` — a single value, not a named export. Destructuring `.User` from it returns `undefined`. Node does not throw at module load time; the crash happens the first time any exported function calls `User.create()`, `User.findOne()`, or `User.findById()` — which is every call to `register`, `login`, `logout`, and `refreshTokens`. Verified:

```
node -e "const {User}=require('./src/models/User.model'); User.create({})"
TypeError: Cannot read properties of undefined (reading 'create')
```

Every other service (`lead.service`, `user.service`, `auth.js` middleware) imports User with `const User = require(...)`. The fix is a one-word change on that line.

## Deal stage bypass via PUT

`updateDealSchema` is `createDealSchema.partial()`, and `createDealSchema` includes `stage: dealStageEnum.optional()`. That means `PUT /api/deals/:id` accepts `stage` and passes it directly to `findByIdAndUpdate` with no validation. A `sales_executive` can:

- Move a deal to `won` with `probability = 0` and no `expectedCloseDate`
- Move a deal to `lost` with no `lostReason`
- Reopen a terminal deal without being an admin

The deal's `pre-save` hook (which stamps `wonAt`/`lostAt`) does not fire on `findByIdAndUpdate`, so terminal timestamps are also skipped. The `updateDealStage` service correctly sets `wonAt`/`lostAt` explicitly in its `updateData` object, but that path is skipped entirely here.

Fix: remove `stage` from `createDealSchema` (and by extension `updateDealSchema`). Stage changes are a domain operation that must go through `PATCH /deals/:id/stage`.

## CORS open fallback

```js
// app.js
cors({
  origin: process.env.ALLOWED_ORIGINS ? process.env.ALLOWED_ORIGINS.split(',') : '*',
  credentials: true,
})
```

The FEAT spec specified `process.env.ALLOWED_ORIGINS?.split(',')`, which would be `undefined` when the env var is absent — browsers would block cross-origin requests (safe default). The implementation substitutes `'*'`, which allows any origin to make credentialed requests. In a development environment with permissive `.env` setup this could allow unintended cross-origin access. The fallback should be `[]` or `false`.

## markOverdueActivities write amplification

`getAllActivities` calls `markOverdueActivities()` before every list query, issuing an `updateMany` on every GET. For a low-traffic CRM this is acceptable, but under load it turns every read into two sequential writes. A scheduled job (or a TTL-based status transition) would be the production approach. Not a blocking concern at this stage, worth noting for the next iteration.

## Test coverage

No automated tests exist. The acceptance criteria rely on `node -e require(...)` smoke tests and one manual hit of `/api/auth/me`. The auth crash would not be caught by any of the defined verification steps because all of them test module loading, not function invocation. A minimal integration test that calls `POST /api/auth/register` would have caught the import bug immediately.
