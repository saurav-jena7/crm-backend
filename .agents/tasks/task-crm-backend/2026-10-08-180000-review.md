# CRM Sales Management System — Backend Pass 2

All three blocking defects from the prior review have been resolved: `auth.service.js` now imports `User` correctly, `updateDealSchema` no longer includes `stage`, and the CORS fallback is `false` rather than `'*'`. This pass reviews the remaining implementation with fresh eyes.

**Watch for:**
- **confirmed** — `PATCH /api/leads/:id/status` has no validator middleware. Any string (or no string) reaches `lead.save()` and the Mongoose enum constraint catches it at the DB layer — but only after a round-trip, and the error message format differs from the Zod-based 400 path every other mutation endpoint uses.
- **confirmed** — `auth.controller.js` sets the `refreshToken` cookie with `secure: process.env.NODE_ENV === 'production'`. In a development environment the cookie is transmitted over plain HTTP, which is intentional for local dev but should be documented in `.env.example` so teams deploying staging over HTTP don't accidentally ship insecure cookies in a near-production environment.
- **possible** — `updateUserSchema` is `createUserSchema.partial()`, which makes `role` optional. `PUT /api/users/:id` can therefore change a user's role. Whether an admin should be able to demote themselves (or the last admin) to `sales_executive` is not guarded anywhere. This could lock out the system if the only admin account is demoted.

**Verdict**: APPROVED

## High-level view

All three prior blocking defects are confirmed fixed. The auth import crash is gone (`const User = require(...)` throughout). The deal stage bypass is closed — `createDealSchema` omits `stage`, `updateDealSchema` inherits that omission via `.partial()`, and all stage changes are routed exclusively through `PATCH /:id/stage` with `updateStageSchema`'s `superRefine` rules. The CORS open fallback is replaced with `false`, which causes browsers to block cross-origin requests when `ALLOWED_ORIGINS` is unset — the safe default.

The lead status update endpoint is the one remaining unvalidated mutation path. Every other write route passes through a Zod schema middleware; `PATCH /:id/status` does not, leaving enum validation to Mongoose. The Mongoose error is caught and formatted by `errorHandler`, so clients do get a 400, but the field path in the error object (`status` from Mongoose's `ValidationError.errors`) differs from the Zod format (`{ field, message }`) that the rest of the API produces. This is a consistency gap, not a security gap.

The transaction in `convertLead` is correct: array-form `Model.create([doc], { session })`, `session.abortTransaction()` in catch, `session.endSession()` in finally. `updateDealStage` explicitly stamps `wonAt`/`lostAt` in `updateData` rather than relying on the pre-save hook (which doesn't fire on `findByIdAndUpdate`) — correct. Security posture is solid: helmet, CORS with restrictive fallback, rate-limiter on `/api`, `httpOnly`+`sameSite:strict` refresh token cookie, `password`/`refreshToken` as `select:false` and stripped by `sanitizeUser`.

<summary>Issues (3)</summary>

1. **Unvalidated lead status mutation** — `PATCH /api/leads/:id/status` has no `validate()` middleware. An invalid enum value produces a Mongoose ValidationError formatted differently from every other 400 in the API. Add `validate(z.object({ status: z.enum([...leadStatuses]) }))` to the route.

2. **Role self-demotion not guarded** — `PUT /api/users/:id` accepts `role` changes (via `updateUserSchema.partial()`). An admin could demote themselves or the last admin account, locking out all admin-only endpoints. Add a guard in `user.service.updateUser` that prevents role changes resulting in zero active admin accounts, or at minimum prevents a user from changing their own role.

3. **Insecure cookie in non-production environments** — `secure: process.env.NODE_ENV === 'production'` is correct behaviour but should be noted in `.env.example` with a comment so staging deployments over HTTPS remember to set `NODE_ENV=production`. Currently `.env.example` sets `NODE_ENV=development` without a note.

## Prior defects — confirmed resolved

`auth.service.js` line 3 is now `const User = require('../models/User.model')` — a direct default import matching the model's `module.exports = User`. Every other service that imports User uses the same pattern. `deal.validators.js` `createDealSchema` has an explicit comment: `// stage intentionally omitted — use PATCH /api/deals/:id/stage to transition stages`. `updateDealSchema = createDealSchema.partial()` inherits the omission. `app.js` CORS config is `origin: process.env.ALLOWED_ORIGINS ? process.env.ALLOWED_ORIGINS.split(',') : false`.

## Unvalidated lead status endpoint

`PATCH /:id/status` in `lead.routes.js` mounts no middleware before `leadController.updateLeadStatus`. The controller passes `req.body.status` directly to `updateLeadStatus`, which does `lead.status = status; await lead.save()`. If `status` is not a valid enum value Mongoose throws a `ValidationError`; `errorHandler` catches it and returns 400 with `{ message: 'Validation failed', errors: [{ field: 'status', message: '...' }] }`. The field path is correct and the status code is right — but the Zod path produces `{ field: 'status', message: '...' }` from `issue.path.join('.')`, while the Mongoose path produces it from `e.path`. They happen to look identical for a flat field, but the discrepancy is that missing/undefined `status` in the body silently passes to `lead.save()` with `undefined`, which Mongoose ignores (no change, no error). A Zod validator would catch `status: undefined` explicitly.

## Role self-demotion gap

`updateUserSchema` is `createUserSchema.partial()`. `createUserSchema` includes `role: z.enum([...])`. Therefore `PUT /api/users/:id` with `{ role: 'sales_executive' }` passes validation and reaches `user.service.updateUser`, which strips `password` and `refreshToken` but not `role`. `findByIdAndUpdate` applies the change. There is no check that the target user is the requester's own account, and no check on the count of remaining active admins. The endpoint is gated to `authorize('admin')` so only admins can reach it, but an admin can still demote all admins including themselves.

## markOverdueActivities write amplification (carried forward, non-blocking)

Every `GET /api/activities` call triggers `Activity.updateMany({ dueDate: { $lt: new Date() }, status: 'pending' }, ...)` before the query. For a low-traffic CRM this is fine. The prior review noted this as non-blocking; it remains non-blocking.
